# Excel Repo Contract Seed

Use this checklist to fill gaps in existing rules or seed a new local contract. Resolve concrete paths in the proposal. When a location or capability hasn't been agreed, record it as pending instead of treating it as configured. The [shared Excel contract](https://github.com/ciahciach/versuni-search-ecosystem/issues/63#issuecomment-7108392518) owns routing and runtime procedure; this document describes the local workflow, not another router.

## Local Paths and Authority

- Point to one location each for the workbook registry, reviewed editable source, generated inventory and existing tracker/knowledge rules (if configured). For a new repo, suggest per-workbook `excel/<id>/source/` and `excel/<id>/inventory/`; create them only when there is content. Don't add alternate locations to an existing repo.
- The repo owns approved managed logic and structure; the workbook owns business data and unmanaged objects. Register each workbook separately with its profile, managed scope, immutable base version/checksum and last approved sync point. With no workbook, there is nothing to register; an existing workbook needs separately approved onboarding and an initial reviewed export before establishing a sync point.
- Keep real workbook bases, checkpoints and required binary companions in access-controlled storage outside Git, pinned by immutable version and checksum. Keep `.frm` and its required emitted `.frx` paired. Keep business data, query results and secrets out of exports and evidence. Block publication if secrets are detected; a redacted preview is not import source.

## Managed Scope

- For Windows desktop Excel v1, identify one `.xlsx` or `.xlsm` per controlled import; no cross-workbook updates, silent format conversion or arbitrary reconstruction. Declare editable, inventory-only and out-of-contract objects. Omissions are not deletions.
- Edit explicitly targeted ordinary formulas and dynamic-array anchors, and existing names without changing scope. Preserve formula dialect, kind, exact pattern membership and exceptions; never write spill outputs or fill blank/constant holes. Stop if changed row positions make exceptions unsafe. Table rebuilds, calculated-column templates, legacy CSE arrays and what-if data tables are not managed edits.
- M edits are limited to existing queries and must preserve load destinations. Report load destinations, connection mappings and model presence without credentials. DAX, connections, PivotTables, validation and formatting are inventory-only. Load changes are a separate explicit Excel-side change on a copy, reviewed before registering a new base and sync point; any data access or refresh needs separate approval.
- Edit existing VBA modules in place, preserving document-module host identity, references and project topology. UserForm code and design require separate native validation on an `.xlsm` copy; HTML prototypes are not import artifacts. Block an affected operation if preservation cannot be verified, without disqualifying unrelated operations.

## Daily Workflow

1. **Export and review.** Use current text without launching Excel when it answers the request. For a new explicit export, use saved workbook state and the shared router. Verify freshness and scope; review Excel-side changes before accepting them as source. Review formula changes by exact target, dialect, kind and exceptions. Inventory edits never schedule workbook writes.
2. **Edit.** Modify only approved managed source; keep the intended diff separate from generated reports. Before any import, compare both the saved base and the proposed source to the last approved synchronization point. Stop on two-sided managed drift, even for apparently disjoint changes. Data-only drift is allowed only if preconditions still hold.
3. **Dry-run.** With no writes, identify the base/hash, target cells or objects, proposed changes, preservation checks and blockers. Use the shared router's classification and qualify the actual backend implementation, version, operation and workbook profile. Stop for an open/locked workbook, invalid base, unsafe targets, unverified preservation, or unavailable qualification. No automatic COM fallback. Approval of setup or dry-run is not approval to save.
4. **Save.** After approval and recheck, apply to a separate copy only. Standard import does not run macros, refresh queries or update links. Keep the original and approved sync point unchanged on failure or uncertainty. Never bypass VBA protection or IRM.
5. **Reopen and verify.** Reopen the saved copy, re-export and compare intended changes and preservation against the approved plan. Saving and same-session readback aren't proof of persistence. Record backend/version/profile and distinct results for dry-run, save, reopen/readback and any separately approved macro, compilation or refresh checks. Mark simulated or unperformed checks as such. Only verified, accepted results can advance the approved sync point.

## First Ordinary Formula Import

`scripts/excel-onboarding.py` supports one existing formula replacement in a synthetic simple XLSX. Use the same private store and approved synchronization point as onboarding. Only committed `ordinary-formulas.json` rows can propose changes. Inventory edits and omitted rows do not propose edits or deletions. The first slice supports arithmetic with numbers and local A1 references, or `SUM` of one local range. Data-only drift can include changed numbers in existing input cells, not changed addresses or structure. The package comparison is conservative: it checks package parts, preserves unrelated formulas, caches, data and metadata, and permits only the target formula/cache and the core modified timestamp to differ after the save. Other differences block rather than being assumed benign.

1. Use the shared Excel entry point linked above. Identify the actual backend, version and Excel build, the policy permission to use it for this operation and fixture, and its matching qualification evidence. Stop if any is missing; neither this CLI nor its tests qualifies or invokes a runtime. On a disposable copy of the exact input, independently authorize and perform a no-op desktop save, closing and reopening it read-only under the shared contract. Keep that saved workbook in the private store. Do not do this on an open workbook or when link, macro, event, refresh-on-open or cross-workbook effects cannot be controlled.
2. Under `<store>/routes/`, record an operator attestation JSON file named `<receipt-sha256>.json` beside the no-op workbook `<receipt-sha256>.xlsx`. Use the SHA-256 of the exact receipt bytes. Fields: `entryPoint`, `backend`, `backendVersion`, `excelBuild`, `qualification` and `authorization` (identifiers or references to evidence); `evidenceClass: "desktop"`; `operation: "ordinary-formula-import"`; `profile: "simple-xlsx"`; `inputSha256` and `noOpSha256` (saved bytes); `commit` (full approved Git commit); `output` (worktree-relative, Git-ignored XLSX path). Record real desktop evidence only. The CLI verifies the receipt's binding and no-op preservation, not the truth of externally attested actions or continuing policy permission.
3. Run `python -X utf8 <script> plan-import <artifact-dir> <output.xlsx> --store <store> --commit <commit> --route-sha256 <receipt-sha256>`. Review both diffs and blockers. Without the receipt the command can show the proposed edit but exits blocked. It does not open Excel or write files.
4. Obtain explicit approval for that plan and recheck the route authorization and workbook locks. Run the same command with `prepare-import` instead of `plan-import` and add `--approved-plan <plan-sha256>`. It repeats the checks before making a byte-exact working copy at the previously unused output path. Immediately before opening that copy, repeat the router's runtime checks and confirm the copy still matches `inputSha256`. Write only the reviewed address, using the qualified route and its copy-only safeguards. Save and close the copy, and record its SHA-256. Never save the source.
5. In an independent desktop session, reopen the saved copy read-only without updating links or running macros/refresh, confirm the formula and expected numeric result, and close without saving. Run `verify-import` with the same arguments as `prepare-import`, plus `--saved <saved-sha256> --reopened <independently-reopened-sha256> --result <independently-read-number>`. Use only synthetic data in the command arguments. The CLI independently reads the saved package, compares its formula and numeric cache with the approval and readback respectively, verifies preservation, and shows the re-export and its manifest digest for review. Keep evidence private until reviewed.
6. Only after explicit acceptance, run `accept-import` with the same arguments as `verify-import` plus `--reviewed <manifest-sha256>`. This rechecks evidence, retains the verified bytes and atomically advances the synchronization point to the copy's path. It does not publish Git artifacts or modify the previous workbook. After a partial or uncertain save, do not resume it or reuse it for acceptance. Once the backend is known to be closed, quarantine the output and retry from unchanged input and a fresh dry-run; if the output path changes, pin a new receipt. An abandoned `accept-import.lock` blocks subsequent acceptance: inspect the synchronization point and ensure no acceptance process remains before clearing it manually.
