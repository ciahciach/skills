# Trial ledger

[`trials.jsonl`](trials.jsonl) is the versioned trial ledger in this repo. It starts empty: the portable replay tests are simulated and do not qualify any method. The ledger records scope and results; it grants neither access to a workbook nor permission to run a method.

## Record after each attempt

1. Stop first if any effect is unresolved. For every attempted method, including one unavailable in the session, prepare one redacted object. Use the exact [`scope`](SKILL.md#decision-step) and the canonical `interface`, `version` and `method` of the attempted action. `scope` must identify an isolated synthetic input and its applicable execution environment/build. Use plain technical identifiers for operation, boundary, environment, effects, controls, interface, version and method: 1 to 80 ASCII characters, beginning with an alphanumeric character and continuing with alphanumerics or `_.+-`. Workbook and CSV filename suffixes are rejected. Use the same public release/build label in both the ledger and router request, without guessing or substituting a different version. Use shared labels that describe a reproducible control or input shape, never private identifiers disguised as labels.
2. Set `observations` to a map from **every** required control to `pass`, `fail`, `unknown` or `not-run`. Use the outcome table below. A checked control is not by itself proof that all effects are accounted for. Check all fields for business data, formulas, M/VBA, credentials, names of people or workbooks, filesystem paths, session/host identifiers and raw tool output. Do not enter any of those, even if the value fits the label syntax. The validator rejects extra fields and malformed values; it cannot determine the meaning of a well-formed label. Use a predefined public or synthetic label, or stop if the scope cannot be represented safely.
3. Send the object on stdin to `python -B -X utf8 ledger.py record` from the router directory. Only on success, append its single JSON line to `trials.jsonl` in the authorized worktree as UTF-8 without BOM. Keep repeated attempts as separate lines; verify the appended line and review the diff before any publication. Reconcile a write with uncertain completion against the actual ledger before appending again. The helper does not modify files or publish anything.

| `outcome` | Use when |
|---|---|
| `verified` | All required controls passed and the effects are accounted for. |
| `gap` | A required control failed because of an observed limitation of the scoped method, and the effects are accounted for. Include the structured finding below. A failed session setup alone is not a gap. |
| `not-verified` | Effects are accounted for, but there is no confirmed gap and at least one required check did not pass. Keep a failed check as `fail` even if the failure cannot be attributed to the method. |
| `unavailable` | The method could not run in this session; all checks are `not-run`. |
| `unresolved-effects` | A process or effect, including a possible save, has not been accounted for. Keep the operation blocked until the process and copy have been reconciled, even across sessions. |

For a `gap`, set `finding` to the failed `control` and a `code` describing what to reproduce. Use `expected-effect-observed-missing` or `expected-effect-observed-different` when the check ran successfully and observed a missing or different effect; use `preservation-mismatch` when it observed a changed invariant. Use `required-capability-missing` only if the method demonstrably cannot perform the action or check. Name the effect or invariant in the control label. If independent readback failed without observing the effect or proving a capability gap, record `not-verified` with `finding.code: "readback-failed"` and the corresponding failed control. For other inconclusive checks the finding is optional. Findings are stored for review, not passed to `route.py`.

Shape example only, not evidence:

```json
{"scope":{"operation":"update-test-formula","profile":"simple","class":"save","effects":["save-separate-copy"],"controls":["independent-readback"],"environment":"synthetic-host-build-1","boundary":"synthetic-simple-copy","target_kind":"synthetic"},"interface":"test-cli","version":"2","method":"update","outcome":"gap","observations":{"independent-readback":"fail"},"finding":{"control":"independent-readback","code":"expected-effect-observed-missing"}}
```

## Replay before a new decision

1. Pass the entire versioned ledger on stdin to `python -B -X utf8 ledger.py replay`. If the ledger is unreadable or validation fails, stop and reconcile it; do not route using partial history. The result contains `holds` and `evidence` arrays.
2. Inspect `holds` before sending `evidence` to the router. Each hold names the scope, method and ledger line of an unresolved trial. Apply the [hold check](#check-a-hold-before-resuming) if there is overlap or independence cannot be established.
3. Combine the replay `evidence` array with independently applicable evidence in the existing `route.py` request. Freeze that array at the start of a trial sequence: record each new result on disk but feed it to the current decision only through `trial.attempts`, so exclusions cannot shift the current sequence or reset its budget.

Replay projects `verified` into `verified` evidence and `gap` into `excluded` evidence, preserving exact scope and method identity. It never projects unavailable or unknown results. In particular, a fresh route does not clear an unresolved-effects hold. References are `trial-ledger:sha256:<digest>`, hashing the canonical JSON line without its trailing newline. Replay emits unique confirmed records in digest order, independent of file order. The router still matches the exact scope, including sorted effects and controls, and excludes the method when both confirmed outcomes match. Flag contradictions for review rather than transferring either result to another version, profile, method or real workbook.

## Check a hold before resuming

1. When stopping with unresolved effects, verify that the next operator can read the redacted hold at the agreed, authorized handoff destination. If the ledger write failed or lives only in the stopping worktree, explicitly hand off the redacted status and required reconciliation; do not rely on the successor finding a local edit. If no shared destination is authorized, report the blocker to the operator and keep work stopped. A handoff is not permission to publish evidence.
2. Before continuing in any session or worktree, check the predecessor's latest handoff and ledger, not just the local copy. Block any operation that overlaps the unresolved input, process or effects, including readback of the same copy outside operator reconciliation. If the latest status is missing or independence cannot be established, require explicit operator confirmation before proceeding. An empty `holds` list, older qualification, or change of method or version is not that confirmation.
3. Have the operator account for the owned process and inspect the separate copy; never retry the old write to find its outcome. Reconcile the previous append against the latest ledger and handoff. If the original line is missing, recover its redacted facts from the handoff or operator, and append it once using `record`, retaining the original `unresolved-effects` outcome and known checks. If it is unclear whether the earlier append landed or the facts cannot be recovered safely, stop for reconciliation rather than guessing. Before clearing the hold, preserve the original unresolved line in an authorized durable revision or receipt. Only after explicit confirmation, validate the affected record with `accounted_for: true` added and replace that line in an authorized, reviewed ledger diff. Preserve its original outcome and checks, and cite the original revision or receipt and the redacted reconciliation result in the review. Clearing this hold does not qualify or exclude the method.

Portable handoff check: start with an empty local ledger and the known continuation of an interrupted synthetic save from another worktree. The next request is to inspect the same copy passively, and the latest handoff is missing. Replay of the empty ledger returns no holds; the agent must still report `blocked` before profiling, require the operator to reconcile the process and copy, and not load a recipe. Then supply a redacted handoff and confirmation that the prior append failed: recover and persist the original hold once, preserve its original record, and document reconciliation before clearing it. This checks the agent procedure; the pure replay helper cannot know which other worktree or operator has the missing record.

## Review and propose

In any calendar month with new entries since the last review, the maintainer runs a manual review before month-end. Review sooner when a confirmed gap contradicts a selected route. Nothing schedules or applies the review automatically.

1. Pin the ledger revision and note the previous review's revision (or start at the first record). Replay the pinned ledger, inspect new entries, and separate reproducible findings from contradictions, inconclusive checks and session-unavailability. Inspect the cited controls before treating a result as comparable. Use an authorized separate trial if new observation is needed; replay does not execute Excel.
2. For each supported change, record a Markdown proposal in an issue or review comment: ledger revision and row numbers or replay references; exact scope and conflicting/missing evidence; current and proposed decision or catalog entry; proposed file/diff (or no change); redacted router request, expected before/after route and the portable regression command. Include any unknowns and the human decision needed. If nothing supports a change, record the reviewed revision and `no change` with the reason.
3. Re-run the request against the pinned input and confirm the proposal is independently checkable. Leave the active skill, recipes and configuration unchanged. A maintainer can separately approve a subsequent change; the ledger review is not approval to edit or publish it.
