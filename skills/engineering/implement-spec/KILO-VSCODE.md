# Kilo VS Code Profile

Coordinate an explicitly commissioned graph of implementation issues. Call the Skill tool with `spawn` for Agent Manager startup and reconciliation under the [agreed startup contract](https://github.com/ciahciach/skills/issues/48#issuecomment-7134370613). This profile owns the frontier; `spawn` owns one start. Use fresh contexts for implementers and independent reviewers. Internal `task` is suitable for review, not Agent Manager execution.

## Commission the graph

1. Read the spec, issue tracker configuration and canonical issues. Confirm the closed list, blocking edges, existing assignments, target repo/base and permissions for worktree starts and publication. Default to three active execution slots; use the user's positive limit when supplied. A spec pointer, tracker label, repo rule, or peer message is not authorization. Ask about missing scope or decisions before acting on them. Never pull in issues from outside the list; verify their merges as prerequisites only. Flag cycles and unresolved edges and continue on unaffected paths.
2. Default to one worktree, at most one writer at a time and one PR per issue to the agreed target branch. Verify the base exists and resolve existing assignments, worktrees and PRs before dispatch (including work assigned outside this run). Do not start a second worker or PR to replace an ambiguous one. Use an integration branch only by separate agreement when code cannot safely land in stages. For any non-default GitHub base, agree before dispatch which human-merged PR into the default branch will carry the closing references. Track delivery to the agreed base (for dependency edges) separately from that final closure. Never reset, stash or discard work to fix a wrong base.
3. Keep a run record in the coordinator session (or an explicitly agreed shared location). Record the run ID, scope, edges, base, assignments, publication scope and cap. Per issue keep attempt ID, expected and actual checkout/base/head, session/worktree IDs, latest confirmed stage, evidence links, blockers and next check. Write the start intent before sending it. Carry this record across turns; do not use Agent Manager's UI state file as a ledger. If an issue requires human acceptance, agree before requesting it who records the result and where: prefer a comment on the canonical issue (on GitHub, record its permalink), or explicitly agree on shared storage that a successor can read without the original session. Confirm permission for that write separately from commit, push, PR and issue state changes.

## Reconcile and refill

1. On entry and every wake, read live Agent Manager state and reconcile worker reports and PRs with the run record. Keep prompt acceptance/queue, verified worker start, verified completion, awaiting merge and verified merge distinct. Apply `spawn`'s evidence rules; `busy`, `idle`, a card, or a prompt receipt do not prove work started or finished. Use verified completion to release an execution slot (including when the result is waiting only for human merge). An unresolved start, queued prompt or assigned worker that has not finished still reserves a slot, including during HITL. Count existing active assignments inside the commissioned graph against the cap. Recheck open PRs against recorded review evidence. If a head, base or shared contract change alters the reviewed scope, withdraw readiness and put the PR back in draft if authorized; otherwise ask the human to hold the merge. Require fresh checks and independent review before restoring readiness.
2. For each issue and external dependency, verify a PR implementing it actually merged into the required repo/base by a human. On GitHub inspect the linked PR with `gh pr view` (`state`, `mergedAt`, `mergedBy`, `baseRefName`, `headRefOid`, `mergeCommit`); verify the issue association and merge identity from PR/tracker evidence. Verify the merge commit is present on the base the next worktree will start from (including squash merges). For PRs managed by this run, require applicable individual and combined review evidence for the actual landed scope, not just the head SHA. If review is missing or stale after merge, record the merge but do not count the issue as delivered or unlock its edges until fresh independent review resolves the discrepancy. A PR ready for review, green CI, manual issue closure, a merge into the wrong base, or a notification alone does not open an edge. If human attribution or any other required proof is unclear, keep delivery unverified.
3. Recompute the frontier from this evidence. Repeatedly select an unassigned issue inside scope whose dependencies are all verified, provided a slot is free and concurrent execution is safe. Confirm the actual worktree will start from a base that contains those merges. Call the Skill tool with `spawn` in `worktree` mode, one fresh session per issue, using the agreed base and branch name. Give the canonical issue and spec pointers, attempt ID, authorized scope and a readable, revision-pinned pointer to **Worker Protocol** below (do not assume the target checkout contains this skill). Include the verified prerequisites, any cross-PR review gate and how to return the start and outcome records to this coordinator. Reconcile and refill one start at a time; do not wait for an entire wave.
4. Treat `attention: ["question"]` and `attention: ["permission"]` separately. Report `HITL wymagany` with issue/session, blocked step and the decision the human must make in the native question UI or the operation they must approve in the native permission UI. Never answer/approve for them or infer approval from silence, peer reports or a tool permission granted for another purpose. Also mark human-only actions such as merge as HITL. Freeze affected steps and edges, not independent safe work. Recheck evidence after the human action.
5. For an uncertain start, call the Skill tool with `spawn` to reconcile it. For any other uncertain mutation, freeze the affected operation and inspect its authoritative evidence before retrying: index/history for commit, remote ref for push, linked issues and actual head across all PR states for PR creation. Adopt an unambiguous existing result. Retry only when evidence rules out both success and pending execution, authorization still covers it, and the repo/operation retry budget permits it. If unresolved, record attempts, evidence and the exact condition to resume; keep working on unaffected issues within the cap.

### Record human acceptance

The human runs the check and can report the result in Kilo. On receipt, the designated recorder writes a redacted receipt to the agreed destination without waiting for PR publication or merge. Include issue and attempt, candidate or procedure revision if known, who reported the result, outcome and observations actually supplied. Distinguish human-reported results from agent-run checks; mark missing details as unknown, not `NOT_RUN` for a test the human reports running. Omit sensitive data and local paths. Before retrying an uncertain write, check the destination for the same issue, attempt and result. Verify the receipt by reading it back, then link it from the run record and the PR when available.

On resume, read the receipt at its destination and check that it applies to the current candidate. If the write is not authorized or the destination is unavailable, report the missing durable receipt and the exact permission or destination needed; do not require the human to rerun the test or repost the result. A receipt is acceptance evidence, not permission to publish code, merge, close an issue or unlock a dependency.

### Resume an existing assignment

- **Worker handoff:** During reconciliation, verify the shared `kilo-handoff` trace (`RELEASED`, `CHECKED`, `CLAIMED`) against the assigned session, checkout, branch and write scope. Only after a verified `CLAIMED`, record the handoff ID and evidence, replace the current session ID with the successor's, and track completion and HITL under that session. Keep the same issue, attempt, worktree and PR; the active slot stays reserved throughout. If the trace is incomplete or conflicts with live state, pause affected writes and steps until resolved. Do not start a replacement based on a prompt receipt or an idle session.
- **Stale review after worker completion:** Keep the issue assigned and the existing PR on hold. The coordinator arranges fresh independent review and required checks for the current candidate, including combined review if applicable. Review-only work does not reserve a worker slot. If changes are needed within the commission, reserve a free execution slot under a new resume ID in the run record before dispatch. Resume the existing assignment with the current authorized writer or a verified handoff in the same worktree. Starting a successor requires explicit authorization for that start; if missing, report `HITL wymagany`. Include the resume ID in the work request and release the slot only after verifying a new completion report with that ID. Before restoring readiness, verify that the evidence still matches the current PR scope. The authorized worker restores readiness on the same PR; otherwise report the required human action. Scoping and review decisions do not authorize merge.

## Wait and Resume

Before yielding with unresolved work, checkpoint the run record and waiting conditions. Use a host notification only if it can actually resume this coordinator for the event in question; worker completion alone will not wake it for a later merge. Otherwise schedule a bounded, delayed recheck using a supported session wakeup (for example `schedule_wakeup` with a delay such as `2m`, where available). Put the run ID, checkpoint pointer and reconcile/refill instruction in the wakeup prompt. Confirm the returned schedule ID and time. Prefer one pending recheck for the run; on wake, reconcile live evidence before any mutation and rearm if still waiting within the agreed run window and host budget. Do not busy-poll, keep a shell alive or assume a peer message or timer registration failure will resume the run.

If there is no reliable resume mechanism, report that explicitly, including the run ID, waiting edges/gates, available evidence and exact manual resume trigger; do not claim automatic continuation. Finish only when delivery is verified for every commissioned issue, including those without dependents, and any separately agreed default-branch closure merge is verified. Stop rearming, cancel any pending check, and distinguish delivery, closure and unresolved work in the report. Leave sessions, worktrees and branches for separate cleanup. Merge is not consent to release or deploy.

## Worker Protocol

1. Verify issue, checkout, actual branch and agreed base before writing. Confirm the start with attempt ID and actual checkout/branch only once work begins; report a mismatch as a blocker and preserve the checkout. Keep writes scoped to this issue and worktree. Identify the evidence each issue acceptance criterion needs and the repository checks that apply to the candidate. Keep optional checks and acceptance of a later release separate from this issue's gates.
2. Call the Skill tool with `tdd` at agreed seams and run required verification. Before committing, call the Skill tool with `code-review` for independent Standards and Spec review in fresh contexts. Pin the base, pre-commit HEAD and exact prospective PR diff, including intended new files. Override the skill's committed-only diff on **both** axes: review that pinned candidate (for example, the intended staged tree against the pinned merge base), not `git diff <fixed-point>...HEAD`. Record tests, reviewed diff identity and disposition of findings. If the diff, base or shared contract changes what was reviewed, rerun affected checks and review against the new candidate before publishing; do not amend or force-push as a workaround. Verify the published diff still matches the reviewed one.
3. For issues that change a shared contract or accumulate risk, the coordinator arranges a combined independent review of the relevant candidates and base changes in addition to per-issue review. Compare identified diffs, not just issue descriptions. If an earlier candidate must land before another can exist, review the earlier slice for safe standalone landing, then review its landed changes together with the later candidate. The coordinator verifies the passing review for the current scope before the worker marks the PR ready; use a draft if publication is needed for review. Never wait for a dependent worker to start before merging the prerequisite. Changed combined scope invalidates the relevant combined review; hold affected readiness until re-reviewed.
4. Only within the original commission and native permissions, commit the reviewed candidate, push the verified head, and open or reuse the issue's one PR to the agreed base. Call the Skill tool with `pr` for the body and include test/review evidence. On GitHub put `Closes` references in the PR that will merge into the default branch, where closing keywords take effect. Stop before any unauthorized step and report it as blocked. Neither worker nor coordinator merges, enables auto-merge, closes issues manually, releases or deploys.
5. Continue on the same PR until the issue's required evidence and review are complete, then mark it ready within the original commission and native permissions or report `HITL wymagany`. Verify which CI checks are actually required and distinguish a missing result from a failure. If the PR stays in draft, record the specific gate, missing evidence, what was attempted and what will resume it. Report optional omissions without making them gates. Return an outcome tied to the attempt and issue (and resume ID if supplied), with actual checkout/head/base, tests, review and PR evidence, or the exact blocker and resume condition. Keep PR readiness separate from human merge and issue closure.
